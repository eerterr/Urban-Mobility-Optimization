# ТЗ: Улучшение модели прогнозирования спроса на велосипеды Divvy

## Контекст
Проект **Urban Mobility Optimization** использует исторические поездки Chicago Divvy за 2024 год. Сейчас построена модель `HistGradientBoostingRegressor`, прогнозирующая количество стартов поездок на станции в следующий час.

Текущий результат на временном holdout:
- Lag 1 baseline: MAE = 0.6483, RMSE = 1.7595
- Lag 24 baseline: MAE = 0.6415, RMSE = 1.8238
- HistGradientBoosting: MAE = 0.4847, RMSE = 1.2037

Модель превосходит лучший baseline по MAE примерно на 24.5%. Датасет содержит около 3.63 млн строк и 1,306 станций.

## Цель
Улучшить качество и надёжность прогноза спроса, не допуская утечки будущих данных. Не гнаться за минимальной метрикой любой ценой: модель должна стабильно работать на разных временных периодах и быть полезной для последующего rebalancing.

## Что оптимизировать
1. **Качество прогноза:** MAE и RMSE; дополнительно WAPE и R², если это уместно.
2. **Стабильность:** качество на нескольких временных validation folds, среднее и разброс метрик.
3. **Практическая полезность:** отдельно оценить busiest stations и peak hours, а не только все station-hours вместе.
4. **Вычислительная эффективность:** найти разумное качество без чрезмерного времени обучения и потребления RAM.

## План экспериментов
1. Проверить и зафиксировать текущие baseline: `demand_lag_1`, `demand_lag_24`, `demand_lag_168`.
2. Реализовать time-series cross-validation (expanding window, 3–4 folds): обучение только на прошлом, validation — на следующем временном периоде.
3. Провести tuning текущего `HistGradientBoostingRegressor`: сравнить несколько значений `max_iter`, `learning_rate`, `max_leaf_nodes`, `max_depth` и `l2_regularization`. Не запускать полный Grid Search на всём датасете; использовать ограниченный Random Search или последовательный подбор на manageable sample, затем проверить лучшие параметры на полных данных.
4. Добавить/проверить feature engineering: cyclical hour/day/month features; дополнительные лаги и rolling statistics (только с shift, без leakage); `station_id`/station-related features — оценить корректный способ кодирования.
5. Сравнить текущую модель с 1–2 дополнительными моделями, например CatBoost или LightGBM (если установка и время позволяют). Не добавлять десятки моделей без необходимости.
6. Если эксперимент покажет потенциал и останется время, исследовать дополнительные годы данных и погодные features. Это вторичный этап, не блокирующий текущую задачу.

## Требования к evaluation
- Только chronological splits; никакого random train/test split для временных данных.
- Все lag/rolling features должны использовать только информацию, доступную до прогнозируемого timestamp.
- Отдельно считать метрики по folds, затем среднее и стандартное отклонение.
- Сравнить модели с baseline на одинаковых folds.
- Провести краткий error analysis: нулевой спрос, busy stations, peak hours, будни/выходные.
- Сохранить итоговую таблицу экспериментов в `results/reports/` (CSV) и подготовить график сравнения моделей/метрик.

## Результат работы
Создать экспериментальный pipeline, который запускается из корня проекта и:
- обучает/проверяет baseline и модели по временным folds;
- выполняет ограниченный tuning;
- сохраняет конфигурации и результаты экспериментов;
- определяет лучшую модель по cross-validation, учитывая MAE, RMSE и стабильность;
- сохраняет краткий вывод с выбранной моделью и её параметрами.
